# ソースの注意点のまとめ

`app/thermo-node`、`app/thermo-gateway`、`app/common` のソースについて、不具合の可能性、文書との食い違い、設計上の注意をまとめた一覧です。詳しい説明は、各文書の「注意点」にあります。ソースの解析で分かったことの記録なので、実機で再現していないものも含みます (実機で確かめたものには、そう書いています)。修正したものは、「修正済み」に移します。

優先度は、影響の大きさの目安です。

| 優先度 | 意味 |
|:---|:---|
| 高 | データが失われる、または機能が止まる可能性がある |
| 中 | 条件がそろうと、期待と違う動きになる |
| 低 | 文書や名前の食い違い、重複、将来の注意 |

## 不具合の可能性

| 優先度 | 内容 | 場所 |
|:---|:---|:---|
| 高 | **publish の送信の成功で、「送信済み」にする。** `sent_count` は、PUBACK を待たずに、`mqtt_publish()` が成功した時点で増える。直後に接続が切れると、ブローカーに届いていない値が、SD カードで送信済みになる | `cloud.c`、`direct.c` |
| 高 | **publish に失敗した値は失われる。** キューから取り出したあとで失敗するので、値は戻らない。セッションは終わり、再接続する | `cloud.c` |
| 中 | **ログの保存が止まると、再開できない。** `sdlog.c` が書き込みに失敗すると、`ready` が false になる。再開するのは `sdlog_start()` だけ。`is_backlog_ready` が true のままだと `thermo sd` は `backlog_init()` を呼ばないので、再起動するまで再開しない | `sdlog.c`、`direct.c` |
| 中 | **溜めた記録を送る速さに上限がある。** `flush_backlog()` は、5 秒に 1 回、キューが 4 件になるまで入れるので、最大で 5 秒に 4 件。1 時間分 (720 件) を送るのに、約 15 分かかる | `direct.c` |
| 中 | **`direct_init()` の失敗は、保存を黙って止める。** アドレスの取得か `cloud_init()` に失敗すると、`is_addr_ready` が false のままになり、`direct_sample()` は何もしない。SD カードをマウントできていても保存しない (`thermo sd` が警告する)。過去には、`cfg_init()` の `-EEXIST` が原因だった | `direct.c` |
| 中 | **RTC の時刻が戻ると、二分探索がずれる。** `backlog_foreach_since()` は、記録が時刻順であることを前提にしている。ゲートウェイが 1 時間ごとに書く時刻が RTC より遅れていると、時刻が戻る | `backlog.c`、`node_time.c` |
| 中 | **グラフの復元の範囲がずれる。** 区切りの境界は、稼働時間と UNIX 時刻とで、最大 1 区切り (既定 170 秒) ずれる。最初の区切りより後に RTC に時刻が入ると、復元しない | `history_store.c` |
| 中 | **WiFi の切断のイベントの順序に依存する。** 切断を要求した直後に接続し直すと、前の切断のイベントが後から届いて、`is_ip_ready` を false にする可能性がある | `wifi_link.c` |
| 中 | **メインループが止まる。** `wifi_time_fetch()` は、最大で約 25 秒 (名前解決を除く) 戻らない。その間、ボタン、測定、通知、OLED が止まる。起きるのは、時刻がないときに 1 分に 1 回、最大 5 回 | `main.c`、`wifi_time.c` |
| 中 | **`cloud_set_enabled(true)` はキューを空にする。** ノードが WiFi を始める前に積んだ値は捨てられる | `cloud.c` |
| 中 | **ノードは、ゲートウェイとスマートフォンに同時にはつながれない。** `CONFIG_BT_MAX_CONN=1` のため。2 にすると、BLE のヒープが増えて WiFi と TLS の分が足りなくなり、直接の送信が届かない (実機で確認。RAM は 99.9% 使われている)。thermo-term の BLE のタブを使うときは、ゲートウェイを止める | `thermo-node/prj.conf` |
| 中 | **スマートフォンの接続も、ゲートウェイの接続として数える。** `ble_is_connected()` は相手を区別しない。そのため、スマートフォンがつないでいる間は、ゲートウェイにつながっているとみなして、WiFi での直接の送信を始めない (測定値は、SD カードに送信済みとして保存される) | `thermo-node/src/ble.c`、`direct.c` |
| 低 | 送信のキューが満杯 (16 件) のときは、新しい値を捨てる。AWS につながらない間のゲートウェイの値は失われる | `cloud.c` |
| 低 | 屋外用ではない SwitchBot も、SwitchBot の記録の枠 (4 台) を使う。アドレスを変えた機器は、別の機器として扱う | `switchbot.c` |

## セキュリティ

| 優先度 | 内容 | 場所 |
|:---|:---|:---|
| 中 | ノードの時刻の特性には、認証なしで書き込める。近くの BLE 機器が、ノードの時刻を変えられる (表示と、SD カードの記録の時刻に影響する) | `thermo-node/src/ble.c` |
| 中 | WiFi のパスワードと秘密鍵は、フラッシュに平文で保存する | `cfg.c` |
| 低 | `thermo set psk <値>` の値は、シェルの履歴とログに残る | `cfg_shell.c` |
| 低 | クライアント ID をそのままトピックに入れる。`+`、`#`、`/` を含むと、階層が変わる | `payload.c` |

## 文書や名前の食い違い

| 内容 | 場所 |
|:---|:---|
| 上書きは、最も古い位置から行う。**送信済みを選んで消す処理はない。** `backlog.h` のコメントの「未送信の記録は最後まで残る」は、ふつうは成り立つが、未送信が上限より多いと、未送信が失われる | `backlog.c`、`backlog.h` |
| `THERMO_WIFI_TIME` の説明は「5 分続いたら」。実装では、起動の 1 分後から 1 分ごとに、最大 5 回 (WiFi を使えないときは、回数に数えない) | `Kconfig`、`main.c` |
| ノードが直接送る値は、**ノード自身のクライアント ID** のトピックに入る。ゲートウェイ経由の値は、ゲートウェイのクライアント ID のトピックに入る。そのため、同じノードの値が、別のトピックに分かれる | `payload.c`、`direct.c` |
| `history_last()` には、ソースの中に呼び出し元がない (単体テストだけ) | `history.c` |

## コードの重複

| 内容 | 場所 |
|:---|:---|
| 温度を「符号と絶対値」に分けて出力する処理が、複数の場所にある | `main.c` (ノード、ゲートウェイ)、`oled.c`、`payload.c` |
| 名前解決と SNTP の問い合わせが 2 か所にある (システム時計を合わせるのは、一方だけ) | `ntp.c`、`wifi_time.c` |
| `is_in_range()` が 2 か所にある | `oled.c`、`rtc_pcf8563.c` |

重複は、各ファイルを自己完結させるための、意図したものと見られます (共通の関数にまとめるときは、`app/common` に置く)。

## 排他制御がない箇所

次の変数は、複数のスレッドから触りますが、ロックはありません。1 ワードの読み書きなので値は壊れませんが、複数の値の組がずれて見えることはあります。

| 変数 | 触るスレッド |
|:---|:---|
| `nodes[]`、`pending_*` (ゲートウェイの BLE) | Bluetooth、システムのワークキュー |
| `connection_count` (ノードの BLE) | Bluetooth、メイン |
| `cfg.c` の `values[]` | シェル、メイン、`cloud` |
| `cloud.c` の `is_mqtt_up` など | Bluetooth、メイン、シェル、`cloud` |
| `wifi_link.c` の `is_ip_ready` | `cloud`、メイン、シェル、ネットワークのスレッド |
| `buzzer.c` の `playing` など | メイン、システムのワークキュー |

## 修正済み

| 内容 | 場所 |
|:---|:---|
| ゲートウェイは、スキャンを止められなかったとき (`-EBUSY` 以外のエラー) に、接続をあきらめたあと、スキャンを再開しなかった。そのため、ノードを見つけられず、再起動するまでつながらなかった (実機で確認)。今は、スキャンを再開する。`-EALREADY` (すでに止まっている) は、成功として扱う | `thermo-gateway/src/ble.c` |
