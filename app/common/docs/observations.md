# ソースを読んで気づいた点のまとめ

`app/thermo-node`、`app/thermo-gateway`、`app/common` のソースを読んで気づいた、不具合の可能性、文書との食い違い、設計上の注意を、まとめました。詳しい説明は、各文書の「気づいた点」にあります。**ソースは、修正していません。** 読んで分かったことの記録で、実機での再現は、していません。

優先度は、影響の大きさの目安です。

| 優先度 | 意味 |
|:---|:---|
| 高 | データが失われる、または機能が止まる可能性がある |
| 中 | 条件がそろうと、動きが期待とずれる |
| 低 | 文書や名前の食い違い、重複、将来の注意 |

## 不具合の可能性

| 優先度 | 内容 | 場所 |
|:---|:---|:---|
| 高 | **publish の送信成功で「送信済み」にする。** `sent_count` は `mqtt_publish()` が成功した時点で増える。PUBACK は待たない。直後に接続が切れると、ブローカーに届いていない値が、SD カードで送信済みになる | `cloud.c`、`direct.c` |
| 高 | **publish に失敗した値は失われる。** キューから取り出したあとで失敗するので、値は戻らない。セッションは終わり、再接続する | `cloud.c` |
| 中 | **ログの保存が止まったあと、再開できない。** `sdlog.c` が書き込みに失敗すると、`ready` が false になる。再開は `sdlog_start()` だけ。`backlog_ready` が true のままだと、`thermo sd` は `backlog_init()` を呼ばないので、再起動するまで再開しない | `sdlog.c`、`direct.c` |
| 中 | **溜めた記録を送る速さの上限。** `flush_backlog()` は 5 秒に 1 回、キューが 4 件になるまで入れる。最大で 5 秒に 4 件。1 時間分 (720 件) で約 15 分かかる | `direct.c` |
| 中 | **`direct_init()` の失敗は、保存を黙って止める。** アドレスの取得、`cloud_init()` の失敗で、`addr_ready` が false のままになり、`direct_sample()` は何もしない。SD カードがマウントできていても、保存しない。`thermo sd` が警告する。過去には `cfg_init()` の `-EEXIST` が原因だった | `direct.c` |
| 中 | **RTC の時刻が戻ると、二分探索がずれる。** `backlog_foreach_since()` は、記録が時刻順であることに頼る。ゲートウェイが 1 時間ごとに書く時刻が、RTC より遅いと、時刻が戻る | `backlog.c`、`node_time.c` |
| 中 | **グラフの復元の範囲。** 区切りの境界は、稼働時間と UNIX 時刻で、最大 1 区切り (既定 170 秒) ずれる。RTC に時刻が入るのが、最初の区切りより遅いと、復元しない | `history_store.c` |
| 中 | **WiFi の切断のイベントの順序。** 切断を要求した直後に接続し直すと、前の切断のイベントが後から届いて、`ip_ready` を false にする可能性がある | `wifi_link.c` |
| 中 | **メインループが止まる。** `wifi_time_fetch()` は最大約 25 秒 (名前解決を除く)、戻らない。その間、ボタン、測定、通知、OLED が止まる。時刻がないときの、1 分に 1 回、最大 5 回 | `main.c`、`wifi_time.c` |
| 中 | **`cloud_set_enabled(true)` はキューを空にする。** ノードが WiFi を始める前に積んだ値は、捨てられる | `cloud.c` |
| 低 | 送信のキューが満杯 (16 件) のとき、新しい値を捨てる。AWS につながらない間のゲートウェイの値が、失われる | `cloud.c` |
| 低 | SwitchBot の記録の枠 (4 台) を、屋外用ではない SwitchBot も使う。機器がアドレスを変えると、別の機器になる | `switchbot.c` |

## セキュリティ

| 優先度 | 内容 | 場所 |
|:---|:---|:---|
| 中 | ノードの時刻の特性は、認証なしで書き込める。近くの BLE 機器が、ノードの時刻を変えられる (表示と、SD カードの記録の時刻に影響する) | `thermo-node/src/ble.c` |
| 中 | WiFi のパスワードと秘密鍵は、フラッシュに平文で保存する | `cfg.c` |
| 低 | `thermo set psk <値>` の値は、シェルの履歴とログに残る | `cfg_shell.c` |
| 低 | クライアント ID を、そのままトピックに入れる。`+`、`#`、`/` を含むと、階層が変わる | `payload.c` |

## 文書や名前の食い違い

| 内容 | 場所 |
|:---|:---|
| 上書きは、最も古い位置から行う。**送信済みを選んで消す処理はない。** 「送信済みの記録から順に消えます」(`SD_LOG.md`)、「未送信の記録は最後まで残る」(`backlog.h`) は、通常は成り立つが、未送信が上限より多いと、未送信が失われる | `backlog.c`、`backlog.h`、`SD_LOG.md` |
| `THERMO_WIFI_TIME` の説明は「5 分続いたら」。実装は、起動の 1 分後から 1 分ごとに、最大 5 回 (WiFi を使えないときは、回数に数えない) | `Kconfig`、`main.c` |
| ノードが直接送る値は、**ノード自身のクライアント ID** のトピックに、ゲートウェイ経由の値は、ゲートウェイのクライアント ID のトピックに入る。同じノードの値が、別のトピックに分かれる | `payload.c`、`direct.c` |
| `history_last()` は、ソースの中に呼び出し元がない (単体テストだけ) | `history.c` |

## コードの重複

| 内容 | 場所 |
|:---|:---|
| 温度を「符号と絶対値」に分けて出力する処理が、複数の場所にある | `main.c` (ノード、ゲートウェイ)、`oled.c`、`payload.c` |
| 名前解決と SNTP の問い合わせが、2 か所にある (一方は、システム時計を合わせる) | `ntp.c`、`wifi_time.c` |
| `is_in_range()` が、2 か所にある | `oled.c`、`rtc_pcf8563.c` |

重複は、各ファイルが自己完結するための、意図したものと見られます (共通の関数にまとめる場合は、`app/common` に置く)。

## 排他制御がない箇所

次は、複数のスレッドから触りますが、ロックはありません。1 ワードの読み書きなので、値が壊れることはありませんが、複数の値の組が、ずれて見えることはあります。

| 変数 | 触るスレッド |
|:---|:---|
| `nodes[]`、`pending_*` (ゲートウェイの BLE) | Bluetooth、システムのワークキュー |
| `connection_count` (ノードの BLE) | Bluetooth、メイン |
| `cfg.c` の `values[]` | シェル、メイン、`cloud` |
| `cloud.c` の `mqtt_up` など | Bluetooth、メイン、シェル、`cloud` |
| `wifi_link.c` の `ip_ready` | `cloud`、メイン、シェル、ネットワークのスレッド |
| `buzzer.c` の `playing` など | メイン、システムのワークキュー |
